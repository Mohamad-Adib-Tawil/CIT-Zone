## خطة التنفيذ بالترتيب

1. تثبيت مسار التشغيل المنشور بين المضيف ومجموعة Vercel: حالياً المضيف معلوم لكن health/config والمسارات البديلة أعادت 404. بعد إصلاح/تأكيد مسار API من مالك Backend، أعد فحص GET health وGET app/config دون هوية أو كتابة. استخدم مسارات Notion؛ الأمثلة القديمة في الخطة 06 مفاهيمية.
2. تثبيت أسماء حقول الطلب والاستجابة والحالات الفعلية للمصادقة والتسجيل والترقيم والأخطاء. يمكن استخراج العقد من مستودع الخادم أو توثيقه أو استجابات القراءة المصرح بها؛ لا تختلق DTO من الوصف العربي.
3. تهيئة سياق الطلب: `X-Device-Id` و`X-Platform` و`X-App-Version`، وBearer للجلسة المناسبة، مع فصل الطلبات العامة. الاتفاق على معنى معرّف الجهاز؛ الترويسة وحدها ليست إثبات جهاز. عدم تسجيل الرموز أو الروابط المحمية.
4. شريحة الجلسة: `POST auth/google` ثم `POST auth/refresh` و`POST auth/logout` و`GET me/session-state`. تبادل Google ID token داخل طبقة data، والتخزين الآمن بعد تعريف حساب الخادم، وتجديد متزامن واحد دون حلقات أو إعادة كتابة عمياء؛ إلغاء نتائج الجلسة السابقة وتنظيف بيانات حسابها عند تبديل الحساب.
5. شريحة التسجيل والجهاز: usage-type/basic-info/academic-info/departments/registration-summary/registration-confirm ثم الجهاز وطلبات تغييره. الخادم يقرر الأهلية والحالة؛ الجلسة المحدودة لا تفتح المحتوى. يلزم توضيح bootstrap/refresh للجلسة المحدودة لأن قائمة السماح في Notion لا تفصلها.
6. الملف والإعدادات والتقويم: me/preferences/push-tokens/academic-status/term-reregistration/exam-schedule. لا تفعيل إشعارات أو تسجيل توكن قبل فحص إعدادات المنصات والخروج والحذف وفق العقد.
7. التعلم: home/subjects/lessons/files/exercises، ثم submissions والتقييم وstudy-time. ترقيم وإلغاء الطلبات القديمة، وحالات تحميل/فراغ/خطأ/دون شبكة/انتهاء جلسة؛ لا إحصاءات صفرية بديلة عند فشل الطلب. فصل العلامات الرسمية عن نتائج تمارين التطبيق.
8. الكورسات والطلبات والقسائم والاشتراكات، ثم العلامات والإشعارات والدعم. Idempotency-Key لـorders وفق المصدر؛ اتفاق مستقل على استعادة نتيجة الكتابة بعد timeout. `payments/shamcash/webhook` خادم لخادم ولا يُستدعى من Flutter.
9. شريحة تشغيل/تنزيل مستقلة بعد اعتماد D08/D09: playback-session/downloads/renew/sync وPDF المحمي. لا MP4 مكشوف أو رخصة افتراضية أو ادعاء DRM من وجود endpoint. ملفات PDF الأكاديمية فقط قابلة للتصدير حسب السياسة.
10. اختبارات عقد وRepository وCubit وحالات الرفض، ثم رحلات Android/iOS مع خادم الاختبار، ومقارنة Figma لكل واجهة متأثرة؛ لا اعتبار اختبارات النقل المحلية دليلاً على ربط الخدمة.

## فجوات العقد المطلوب حسمها

- endpoint صحي منشور فعلياً وبيئة اختبار وإصدار عقد؛ المضيف معروف، لكن المسارات المقروءة عليه لا تصل إلى routes حية. سبب ظهور `GET /api` في رسالة 404 غير محسوم من العميل وحده.
- JSON body/envelope، المعرفات وnullability والتواريخ وأكواد HTTP، ترقيم القوائم، ومخطط الأخطاء؛ المحول الحالي يفترض object و`error.code` ولا يوجد ما يثبت مطابقته للخادم.
- تدوير refresh وإبطاله واستعادة الجلسة وتوجيه session-state، وحالات التوكن المحدود والحساب الموقوف.
- إنشاء معرّف الجهاز وإثباته وقيم platform/version، ودعم الجهاز القديم دون إضعاف الحماية.
- `subjects?scope=current|previous` لا يصف كتالوج كل الأقسام المعتمد؛ يلزم توثيق طلبه. تقدير اختيار المحاولات وحساب التراكمي والأسبوع في D18/D22/D27 لا يحسمه عنوان endpoint.
- تفصيل grades يذكر التمارين؛ يجب توضيح إن كان يعرضها منفصلة عن العلامة الرسمية. إرسال حلول تمارين الكورسات مؤجل في التحليل؛ لا يُفعّل تلقائياً عبر مسار submissions العام.
- رفع إيصال الدفع: التحليل يذكر إيصالاً، وStudent API يذكر رقم العملية؛ تثبيت payload وآلية رفع المرفق قبل التنفيذ.
- رخص الفيديو وPDF والأوفلاين ومزودها وصلاحيتها وتجديدها تحتاج عقود المنصة والخادم المعتمدة.

## الملفات المتوقع تأثرها بعد توفر العقد

تُثبت الأسماء النهائية في بطاقة كل شريحة قبل الكود: `lib/core/network/` لسياق الطلب وتجديد الجلسة؛ `lib/features/auth/` لتبادل الهوية؛ `lib/core/security/` لتخزين أسرار الجلسة؛ `lib/app/di/app_dependencies.dart` و`lib/app/router/` لحقن وتنقل الجلسة؛ مجلد feature مستقل لكل مجال وفق البنية الحالية. تستعمل Result وCubit وApiClient القائمة دون إضافة حزم الآن. Android/iOS والتوقيع وpush وDRM تعدل فقط في الشريحة التي تحتاجها. لا تغيير SQL المحلي أو اختيار تقنية الخادم بالاستنتاج.
