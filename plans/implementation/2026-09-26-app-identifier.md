# بطاقة مهمة — توحيد معرّف التطبيق

- **القسم والخطة:** أساس التطبيق وهوية Google؛ `features/01-foundation.md` و`features/02-identity-devices.md`.
- **الهدف:** يظهر تطبيق Android وiOS بالمعرّف الذي قدمه صاحب المنتج: `com.devmind.cit.learn`، ليطابق تسجيل OAuth والتوقيع المستقبلي.
- **داخل النطاق:** `applicationId` و`namespace` وحزمة `MainActivity` على Android، وBundle ID للتطبيق والاختبارات على iOS، ووثيقة إعداد Google. **خارج النطاق:** إنشاء مشروع Google Cloud، معرّفات OAuth، توقيع إصدار المتاجر أو تعديل معرّف معاينة macOS.
- **القرار:** سجل القرار بتاريخ 2026-09-26 في `plans/09-decisions.md` بناءً على رسالة صاحب المنتج. لا يغير D07 أو سياسة الصلاحيات.
- **الصلاحيات والرفض:** لا يفتح المعرّف أي وصول؛ تسجيل Google يبقى غير مهيأ حتى إنشاء عميل OAuth مطابق على Google Cloud، والتحقق/الدور يبقيان على الخادم.
- **كيانات وقيود:** معرّف Android وiOS ثابت في إعدادات البناء؛ تغييرهما بعد نشر التطبيق يتطلب تطبيقاً جديداً أو خطة ترحيل، ولم تُثبت نسخة منشورة الآن.
- **عقد API:** لا تغيير في الطلبات أو الاستجابات. Google OAuth Android يحتاج package name وبصمة التوقيع، وiOS يحتاج Bundle ID وURL scheme المطابقين.
- **الحالات البصرية:** لا تغيير واجهة؛ خطأ إعداد OAuth يظل واضحاً عند غياب القيم.
- **الملفات:** Gradle وKotlin وXcode و`plans/implementation/google-oauth-setup.md`؛ لا ترحيلات أو تبعيات Flutter.
- **الاختبارات:** فحص نصوص الإعدادات ومسار Activity، `flutter pub get --enforce-lockfile`، التنسيق والتحليل والاختبارات، بناء Android وiOS المتاحين.
- **الأداء:** لا تغيير متوقع.
- **القبول:** APK وiOS simulator يبنيان بالمعرّف الجديد، و`MainActivity` يحل بشكل صحيح؛ وثيقة OAuth لا تشير للمعرّف القديم. تسجيل Google الحقيقي ما زال ينتظر Project ID ومعرّفات العملاء.
