# 11 — عقد الالتزام بتصميم Figma والخطط والبيانات

**اعتماد التعليمات: 2026-10-15، بطلب صاحب المشروع.** يسري على إنشاء الواجهات وتعديلها وإصلاحها ومراجعتها وإعادة هيكلتها في Hasobjy / حاسوبجي. يطبقه كل مساعد يقرأ [AGENTS.md](../AGENTS.md) أو [قاعدة المشروع الدائمة](../.cursor/rules/hasobjy-design-contract.mdc).

## 1. المراجع وحدود كل مرجع

- تعليمات صاحب المشروع المباشرة الأحدث هي المرجع عند تعارضها مع تعليمات المستودع؛ دوّن أثر أي استثناء صريح في بطاقة المهمة وسجل القرارات عند تغيّر قرار المنتج.
- **الشكل المرئي:** إطار Figma الفعلي وحالاته وأصوله ومتغيراته المعتمدة. مطابقة الألوان والخطوط والأوزان والأبعاد والمسافات والمحاذاة والحدود والظلال والأيقونات والصور مطلوبة بدقة.
- **السلوك:** [فهرس الخطط](README.md)، [خطة الميزة](features/README.md)، [المتطلبات المعتمدة](10-notion-requirements.md)، و[سجل القرارات](09-decisions.md). النص التجريبي أو زر في Figma لا يعتمد API أو قرار منتج أو صلاحية.
- **بنية البيانات:** [دليل قاعدة البيانات](../database/README.md)، SQL المعني، [ERD](../database/erd/README.md)، و[قاموس البيانات](../database/data-dictionary.md)، وفق القيود والقرارات المعتمدة. المخطط المحلي لا يثبت وجود قاعدة منشورة أو API أو تفويض خادمي.
- **التنفيذ:** المعمارية الحالية والمكونات المشتركة مصادر لإعادة الاستخدام. المكون القائم لا يبرر اختلافه عن Figma؛ أصلح المكون المتأثر أو استخرج مكوناً مطابقاً ضمن النطاق.

وجود معلومة في مرجع لا يلغي حدود المرجع الآخر. إذا تعارضت المراجع، دوّن النصين ومصدرهما والأثر والقرار المطلوب؛ لا تعدّل التصميم أو الخطة أو SQL لإخفاء التعارض.

## 2. قراءة إلزامية قبل الكود

1. اقرأ `AGENTS.md` و`plans/README.md` و`plans/features/README.md` و`plans/features/00-execution-contract.md` وخطة القسم وسجل القرارات.
2. راجع قصة المستخدم ذات الصلة في `plans/10-notion-requirements.md`، ومخططات التدفق والحالات والمعمارية المرتبطة بها.
3. اقرأ دليل قاعدة البيانات وERD والقاموس وSQL للكيانات التي تقرأها الشاشة أو تعدلها. في تصحيح بصري صرف، سجل عدم تغيير عقد البيانات وسبب عدم الحاجة إلى تعديل السكيما.
4. افحص المكونات وTheme والخطوط والأصول والتوجيه وCubit وRepository والعقود الحالية. لا تكررها ولا تعِد هيكلة أجزاء غير متأثرة.
5. املأ [بطاقة المهمة](features/00-execution-contract.md): النطاق، الإطارات، السلوك، الحالات، الصلاحيات، تتبع البيانات، الاختبارات ومعيار القبول.

## 3. جلب التصميم عبر Figma MCP

1. حمّل مهارة Figma design-to-code المتاحة قبل `get_design_context`.
2. استدعِ `get_metadata` للملف دون nodeId لاكتشاف الصفحات، ثم افحص كل صفحة مطلوبة. إذا اختصرت قائمة الجذر الصفحات، افحص روابط الصفحات الفعلية المتاحة؛ لا تستنتج أن الغلاف يمثل بقية الملف.
3. سجل أسماء الإطارات الموجودة فعلياً وnodeId لكل منها وأبعادها. لا تُنشئ شاشة من اسم في الغلاف أو من رقم مفقود في التسلسل.
4. لكل شاشة استخدم رابط إطارها نفسه في `get_design_context` مع Flutter/Dart وطلب Screenshot والسياق المرئي. إذا كان الرد مقتضباً، افحص الأبناء المطلوبين واجلب سياقهم ولقطة الشاشة قبل التنفيذ.
5. افحص `get_code_connect_map` عند توفره وأعد استخدام المكونات المرتبطة التي تطابق التصميم. غياب الخرائط لا يجيز اختراع تصميم بديل.
6. استخدم `download_assets` للأصول المطلوبة وخزنها محلياً وسجلها في pubspec عند الحاجة. احتفظ بنسب SVG وviewBox والحجم الفعلي والتحويلات مثل الانعكاس والقص؛ لا تستبدلها بأيقونة مشابهة أو أصل مولد.
7. سجل تاريخ الجلب ومصدر كل لقطة وأصل. تقارير المقارنة القديمة أدلة تاريخية؛ أعد التحقق من الإطار الحالي عند تغييره.

## 4. ربط كل شاشة بالسلوك والبيانات

اكتب مسار تتبع صريحاً في بطاقة المهمة أو مستندها المرتبط:

```text
الشاشة / nodeId / الحالة المرئية:
قصة المستخدم / خطة الميزة / القرار المعتمد:
الإجراء / الدور / حالات النجاح والرفض والفشل:
Cubit / use case / Repository المسؤول:
API: العقد المعتمد وحقول الطلب والاستجابة، أو غير متوفر:
كيان المجال / جداول SQL / الحقول / العلاقات / القيود / View أو Trigger المعني:
مخطط التدفق أو ERD / الهجرة المطلوبة إن وجدت:
اختبار السلوك والعقد / دليل المقارنة المرئية:
غير المنطبق وسببه / التعارض أو القرار المعلق:
```

- لا تغير سياسة الاشتراك أو الجهاز أو التنزيل أو العلامات أو التقدم أو حقوق الوصول لمطابقة بيانات نموذجية في الرسم.
- لا تربط Widget بالمخزن مباشرة، ولا تمنح دوراً من اختيار محلي، ولا تجعل نجاح العرض دليلاً على نجاح API أو الحفظ أو التفويض.
- عند غياب الخادم، تبقى قيم الإطار داخل اختبار أو debug واضح؛ لا تعرض نجاح عملية حقيقية أو بيانات مخترعة في الإنتاج.
- عند الحاجة إلى تغيير البيانات، راجع أثره في المجال وDTO وAPI وCubit والتوجيه وDI والاختبارات والترحيلات. حدّث الملفات المتأثرة فعلاً فقط.
- اتبع مسار `database/build.py` و`database/amendments.sql` كما يحدده دليل البيانات؛ احفظ `database/source/` الخام، وأعد توليد schema وERD والقاموس عند تعديل تمثيل البيانات. لا تعدّل ERD أو schema المولد وحده، ولا تنشر قاعدة تلقائياً.

## 5. ضوابط التنفيذ المرئي

- نفذ الترتيب والنسب والأحجام والألوان ودرجات النص ومسافات الأسطر والحروف والمحاذاة والحدود والظلال والأصول وحالات الاختيار وفق المصدر، دون تحسينات ذوقية غير مطلوبة.
- افحص RTL واتجاه كل Row والنصوص العربية والأرقام والبريد والهاتف؛ لا تفترض أن `start/end` تطابق الجانب الفيزيائي المطلوب.
- امنع تسرب تباعد حروف Material أو حواشي الحقول أو حدود الثيم العام إلى التصميم. حمّل الخط الحقيقي في اختبارات العرض.
- حافظ على المقاس المرجعي عند عرض الإطار، واسمح بإعادة الالتفاف والتمرير على المساحات الأصغر ومع تكبير النص ولوحة المفاتيح. لا تعالج overflow بتصغير الخط أو تغيير أبعاد المرجع أو تعطيل تكبير النص بصمت.
- استخدم شريط النظام وSafeArea في المسار العادي؛ وثّق أي وضع تصوير مرجعي يعزل شريط Figma أو مقاسه. لا تكرر شريطين ولا تخفِ اختلاف الجهاز بحيلة في واجهة الإنتاج.
- لا تستخدم Screenshot كواجهة، أو روابط أصول مؤقتة في التطبيق، أو بيانات بديلة لتجاوز نقص حالة وظيفية.

## 6. النقص والتعارض وشرط التوقف

- **إطار الشاشة غير موجود أو MCP غير متاح أو اللقطة ناقصة:** أوقف الجزء البصري المعتمد عليه، واذكر الصفحات والإطارات التي أمكن التحقق منها، واطلب رابط الإطار المطلوب أو إتاحة الوصول. لا تخمن الشاشة.
- **حالة تفرضها الخطة بلا تصميم معتمد:** سجل الحالة الناقصة واطلب مرجعها أو اعتماداً صريحاً لإعادة استخدام نمط قائم. يمكن إنجاز منطقها واختباراته المستقلة، لكن لا تختلق لها واجهة إنتاجية.
- **تعارض Figma مع السلوك أو الصلاحيات أو SQL/ERD:** سجل التعارض والقرار المطلوب في `plans/09-decisions.md` قبل تنفيذ الجزء المتوقف عليه. نفذ العمل المستقل؛ لا تحسم قراراً مانعاً أو تعيد كتابة مصدر خام.
- **استثناء معتمد من صاحب المشروع:** وثّق ما تغير ولماذا وأي إطار/حالة يتأثر؛ حدّث الخطة ومعيار القبول والبيانات إن تأثرت، دون وصف الاستثناء بأنه مطابق للمرجع الأصلي.

## 7. بوابات القبول والتسليم

1. لكل شاشة منفذة مرجع إطار فعلي ولقطة حديثة وأصول محلية ومسار تتبع للخطة والبيانات.
2. شغّل التطبيق على الجهاز أو المحاكي المناسب، والتقط كل إطار عند أبعاده وبحالة وبيانات ومقياس نص مماثلة للمرجع. احفظ صوراً جنباً إلى جنب وتراكباً، وأصلح الاختلافات قبل التسليم.
3. افحص 320 وعرضاً أكبر، وRTL وتكبير النص والحقول ولوحة المفاتيح والتمرير والاختيار والحالات المتأثرة. لا تعتمد فحص عدم الانهيار وحده.
4. نفذ فحوص FVM المحددة في تعليمات المشروع والاختبارات المناسبة للعقود والصلاحيات والبيانات والمنصات المتأثرة. لا تضعف اختباراً أو تغير التصميم لجعل الاختبار يمر؛ أصلح السبب.
5. عند تغير SQL، أعد التوليد ونفذ التحقق المحلي المناسب واختبارات القيود والعقود؛ تبقى اختبارات الخادم المنشور والتزامن وDRM مستقلة.
6. سلّم الملفات والشاشات وnodeId، وأدلة الصور ونتائج الفحوص، والفروق المتبقية وأسبابها وأي قرار أو إطار أو خدمة ناقصة. المتوسط البكسلي المحسوب عبر الخلفيات ليس نسبة مطابقة للتصميم.

لا توصف المهمة بأنها مطابقة أو جاهزة للإنتاج إذا بقي فرق تصميمي غير معتمد أو قرار مانع أو تكامل لازم غير منفذ. فروق تنعيم الخطوط وشريط النظام توثق بأدلة وحدود واضحة.
