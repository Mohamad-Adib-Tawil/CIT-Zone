# 11 — خادم API الخاص والبيانات والتشغيل

## تحديث النطاق 2026-10-08

هذا الاعتماد هو المرجع عند قراءة التفاصيل أدناه؛ تفاصيل التشغيل المعلقة في سجل القرارات لا تُستنتج من أمثلة العقود السابقة.

API يخدم Flutter الطالب ولوحة ويب مستقلة. كتالوج كامل منشور وتوصيات فصل منفصلة دون قيد قسم على شراء المادة، تقويم/billing واستثناء إعادة، وعوامل OCR/Gemini وأحداث إشعارات ودعم. تفصل مهام استخراج OCR الطويلة عن اعتماد علامات بمعاملة وعن إصدار استحقاق. المفاتيح على الخادم، والرفع خاص ومفحوص، ولا تخزن صور كشف في حاوية عامة.

ضع outbox أو معالجة أحداث موثوقة عند الحاجة لمنع الإشعار قبل نجاح الاعتماد، وسياسة إعادة محاولة ومهلة وحد تكلفة. اختيار اللغة والمزود وقاعدة البيانات والويب ما زال D07 التقني. المنصة جهة واحدة، لا tenant أو multi-tenant migrations بالتخمين. اختبارات تفويض وتزامن ودفع وOCR وكتالوج وعلامات ورسائل مطلوبة قبل إطلاق عملاء حقيقيين.

**القرار المحسوم:** صاحب المنتج اختار خادم API خاص. لغة الخادم، الاستضافة، قاعدة البيانات، خدمة الهوية الوسيطة ومزود الفيديو لم تُحسم؛ لا تستنتجها من كون Flutter هو العميل. اقرأ [المعمارية](../02-architecture.md)، [عقود الإدارة](../06-admin-api.md)، [الأمن](../04-auth-security.md)، [الجودة](../08-quality.md) وD07/D08.

## ترتيب بناء الخادم

1. **قرار التقنية:** قيّم مرشحين للخادم/قاعدة علائقية وفق خبرة الفريق، تكلفة التشغيل، دعم المعاملات والقيود والفهارس، الاختبار المحلي، النسخ الاحتياطي، والقدرة على تشغيل معالجة webhook. سجل الاختيار وأسباب رفض البدائل في D07 قبل scaffold دائم.
2. **هيكل طبقات:** route/transport يحول الطلب، middleware يثبت الهوية، authorization يفحص الدور/الحق، application service ينفذ use case، domain يملك القيود، repository/database ينفذ المعاملة. لا تضع قاعدة «الدرس الأول مجاني» في route أو Flutter وحدهما.
3. **مخطط البيانات وترحيلات:** users، device bindings/sessions، departments/years/terms/subjects/placements، instructor profiles، courses/lessons، media/assets/attachments، entitlements، device requests، audit. مفاتيح خارجية وفريدية وفهارس وحقول `createdAt/updatedAt/version`; سياسات حذف/أرشفة تحافظ على الحقوق والرخص القديمة.
4. **عقد API:** OpenAPI أو عقد مكافئ مراجع ومثبت الإصدار؛ مثال نجاح/خطأ لكل route، cursor/limit/order، حقول الوقت UTC، رموز فشل مستقرة و`requestId`. افصل public/student/admin واحتفظ بتوافق إصدار تطبيق قديم خلال فترة نشره.
5. **هوية وتفويض:** تحقق Google ID token على الخادم، جلسات قصيرة/تجديد آمن، ربط جهاز ذري، صلاحيات إدارة منشأة تشغيلياً، حدود معدل، حماية طلبات كتابة متكررة بـidempotency keys، وتدقيق. لا يعتمد التفويض على إخفاء الواجهة.
6. **وسائط:** إصدار تذاكر رفع محددة؛ webhook موثوق ومقاوم للتكرار؛ حالة processing/ready/failed؛ إصدار playback/offline license بعد فحص الحق والجهاز؛ مرفقات في مخزن خاص. مفاتيح المزود في secret manager فقط.
7. **تشغيل:** بيئات dev/staging/prod مع أسرار مستقلة، CI ترحيلات/اختبارات/فحص تبعيات وأسرار، مراقبة p95/errors وفشل الترخيص/المعالجة، نسخ احتياطي مشفر وتجربة استعادة، خطة تدوير مفاتيح وإبطال جلسات، وسياسة احتفاظ/حذف بيانات.

## قواعد قاعدة البيانات والتزامن

- معاملات فريدة على ربط جهاز نشط، موضع مادة، دورة منشورة فعالة، ترتيب درس، ومنح حق متداخل حسب السياسة. افحصها في DB أيضاً حتى إن تحقق التطبيق والخدمة قبلها.
- كل كتابة حساسة تسجل audit في المعاملة نفسها أو عبر outbox موثوق؛ لا تنجح الكتابة وتفقد سجلها بصمت. webhook مكرر أو رسالة عامل معادة يجب أن تكون idempotent.
- `version` أو ETag على محرر الدورة وعمليات الإدارة لتفادي كتابة متأخرة فوق تعديل أحدث. `409` يرجع نسخة/مرجعاً يسمح بالمراجعة دون كشف أسرار.
- لا تفسر `now` من جهاز الطالب كوقت انتهاء الحق؛ الوقت من الخادم وUTC، مع اختبارات حدود الفترات.

## نموذج فشل موحد مقترح

```json
{
  "error": {
    "code": "ENTITLEMENT_EXPIRED",
    "message": "Safe localized or localization-key message",
    "requestId": "opaque-id",
    "details": {}
  }
}
```

هذا مثال عقد، وليس schema نهائياً. `details` قائمة محددة لكل رمز بلا معلومات حساسة؛ لا تعرض stack trace أو استثناء قاعدة بيانات. الاتفاق النهائي يثبت قبل تنفيذ العميل والخادم بالتوازي.

## اختبارات وإطلاق

- Unit للقواعد؛ integration على قاعدة مماثلة للإنتاج للقيود والمعاملات والتزامن؛ contract لكل route ومثال OpenAPI؛ اختبارات رفض طالب/زائر/جلسة منتهية؛ اختبارات حمل على البحث والترخيص والرفع؛ تجربة فشل مزود؛ استعادة backup.
- قبل prod: تهيئة TLS، أسرار، حد معدل، مراقبة وتنبيهات، مراجعة وصول المسؤولين، نشر staging بعينة غير حساسة، خطة ترحيل/رجوع، واختبار تطبيق قديم على API جديد.
- **يقبل** عندما تنجح رحلة كاملة من Google إلى كتالوج ونشر إداري واستحقاق وتشغيل مصرح، ويفشل كل وصول غير مصرح به، ويمكن استعادة البيانات وتتبع الإجراء دون كشف أسرار.
