# 02 — تسجيل Google والأدوار والجهاز الواحد

## تحديث النطاق 2026-10-08

هذا الاعتماد هو المرجع عند قراءة التفاصيل أدناه؛ تفاصيل التشغيل المعلقة في سجل القرارات لا تُستنتج من أمثلة العقود السابقة.

Google إلزامي ولا هاتف/OTP. بعد إصدار جلسة: إكمال `StudentAcademicProfile` بقسم وسنة وفصل وطلبات مواد إعادة. بيانات المسار تستخدم لترشيح مواد الفصل؛ تغيير مرشح القسم يسمح بتصفح بقية الأقسام ولا يغير الحقوق أو الملف. سياسة النقل يدوية فقط عبر دعم ثم تفويض أدمن؛ تعارض الجهاز لا ينشئ جلسة محتوى. لا نقل ذاتي ولا إعادة ربط تلقائي بعد logout. الأدمن بصلاحية واحدة في ويب مستقل؛ تصميم تسجيله وجلساته بعد اختيار التقنية.

اختبر نجاح/رفض إكمال ملف ناقص أو قسم غير صالح، وتصفح قسم آخر دون تغيير الملف أو الحقوق، وإرسال طلب إعادة لا يمنح اشتراكاً، ومسار دعم يعمل مع رفض الجهاز دون تجاوز. التوثيق السابق الذي يجعل D03/D11/D15 مفتوحة يُقرأ وفق سجل الاعتماد الحالي.

**الهدف:** طالب يدخل بحسابه على جهاز نشط واحد وفق سياسة قابلة للاستعادة؛ الإدارة تدخل بدور يصدر من الخادم. لا يوجد حساب أستاذ في MVP.

## قرارات وأساس

اقرأ [الأمن](../04-auth-security.md)، [الخادم](11-backend-operations.md)، وD06/D10/D11/D15. قبل التنفيذ حسم المنصات، دعم أجهزة بلا Google، مسار نقل الجهاز والتحقق، وسياسة المسؤولين. لا تعتبر Google Sign-In تفويضاً للإدارة أو إثبات جهاز.

## نموذج المجال والعقد

- `User(id, googleSub, role, status)`؛ `DeviceBinding(userId, publicKey, status, boundAt, revokedAt, version)`؛ `Session(id, userId, deviceBindingId, expiresAt, revokedAt)`؛ `DeviceTransferRequest(id, status, reason, evidencePolicy, createdAt)`.
- `POST /auth/google/exchange` يستقبل ID token وتحدي/إثبات جهاز وفق العقد النهائي؛ الخادم يتحقق من التوقيع و`iss/aud/exp` و`sub`، ثم يقرر الربط داخل معاملة. لا يقبل `userId` أو `role` المرسلين من العميل كمصدر حقيقة.
- رموز الفشل المقترحة: `AUTH_INVALID_TOKEN`, `SESSION_EXPIRED`, `DEVICE_CONFLICT`, `DEVICE_ATTESTATION_FAILED`, `ACCOUNT_DISABLED`, `ROLE_FORBIDDEN`, `TRANSFER_PENDING`. ثبتها في OpenAPI قبل البرمجة.
- سياسة refresh/logout/revoke تحدد مدة الجلسة، تدوير refresh token وإبطاله، ومعاملة تغيير الجهاز. لا يخزن التطبيق Google ID token كجلسة تطبيق دائمة.

## تنفيذ الخادم

1. أعد تهيئة Google الرسمية للمنصات المستهدفة، وخزن client IDs المسموحة على الخادم. اربط `sub` لا البريد؛ البريد/الاسم حقول عرض قابلة للتغير.
2. خزّن المفتاح العام للجهاز وقيد «ربط نشط واحد لكل طالب» داخل معاملة مع قيد قاعدة بيانات مناسب؛ اختبر سباق أول دخولين متزامنين. سياسة الإدارة مستقلة عن حد الطلاب.
3. تحقق من إثبات سلامة الجهاز والتحدي والتوقيع وفق المنصة، لكن وفر مسار دعم للأجهزة غير المدعومة حسب D06. رفض الإشارة الضعيفة أو قبولها قرار مخاطرة موثق، لا `if` صامت.
4. امنح دور الإدارة تشغيلياً خارج التسجيل العام، سجل من منحه وسحبه، وافحصه على **كل** مسار إداري. عند نقل الجهاز أبطل الجلسات القديمة وإصدار الروابط والرخص الجديدة فوراً؛ لا تدّعِ محو الرخص القديمة غير المتصلة.
5. طبّق حدود معدل وتدقيقاً لمحاولات الدخول والنقل، مع حجب الرموز ومفاتيح الجهاز الخاصة من السجلات.

## تنفيذ Flutter

`features/auth/{domain,data,presentation}` و`features/device_binding/...` عند ظهور حدود مستقلة. واجهات: ترحيب/Google، حالة التقدم، تعارض الجهاز، طلب نقل/انتظار، جلسة منتهية، خروج. Cubit منفصل للجلسة وطلب النقل. احفظ أسرار الجلسة في مخزن النظام الآمن؛ المفتاح الخاص لا يغادر Keystore/Keychain. لا تضع تحقق الدور في Widget وحده.

## اختبارات ومصفوفة قبول

| الحالة | النتيجة المطلوبة |
| --- | --- |
| Google token صحيح + أول جهاز | جلسة طالب وربط واحد |
| token مزور/منتهٍ/لجمهور آخر | رفض بلا إنشاء مستخدم أو جلسة |
| دخولان متوازيان من جهازين | جهاز نشط واحد فقط، الثاني `DEVICE_CONFLICT` |
| طالب يطلب مسار إدارة مباشرة | `403` حتى مع تعديل العميل |
| نقل معتمد | الجلسة القديمة لا تنشئ ترخيصاً أو تشغيلًا جديداً |
| رخصة أوفلاين قديمة | سلوكها ضمن المدة المعلنة، لا وعود إبطال فوري |
| إعادة تثبيت/فقدان جهاز | مسار دعم واضح، بلا تجاوز ذاتي غير معتمد |

شغّل اختبارات العقد والمعاملة على قاعدة اختبار مماثلة للإنتاج، Widget للحالات، وتكامل Android/iOS حقيقي لتسجيل Google والتخزين والإثبات. **لا يُقبل** عرض لوحة الإدارة إنتاجياً قبل إثبات رفض الطالب لجميع مساراتها.
