# 04 — تنفيذ لوحة الويب وتسليمها

قرار D11 بتاريخ 2026-10-08: تطبيق ويب منفصل، RTL ومتجاوب ويمكن إدارته من متصفح الجوال. تقنية الويب معلقة في D07/D11 التقني؛ لا يفترض Flutter Web أو React. معاينة Flutter السابقة مرجع بصري ومفاهيمي فقط.

## مراحل التسليم

1. اعتماد التقنية وبيئة الويب ودخول الأدمن وعقود API، ثم shell متجاوب ومكونات وحالات loading/empty/error/expired/conflict. إذا استُخدم Flutter Web يحتفظ Cubit؛ التقنية الأخرى تتبع فصل العرض والخدمات والمجال دون فرض Cubit عليها.
2. المنهج والمواد وPDF والدورات والدروس والرفع والنشر والتقويم مع فحص خادم وتعارض نسخة.
3. الطلاب والأجهزة والاستحقاقات والإيصالات، والقسائم إذا اعتُمدت، مع تأكيد أثر وتدقيق ومنع تكرار.
4. الإعلانات والإشعارات والدعم والتمارين والتقييمات والتقارير.
5. استيراد صور العلامات: رفع → فحص → استخراج → مطابقة → مراجعة → اعتماد → نتائج وكشف؛ لا نشر من OCR مباشرة.
6. قبول متصفح حاسوب وجوال، لوحة مفاتيح وقارئ شاشة وRTL ونص كبير، وشبكات ضعيفة وإعادة تحميل الروابط والتراجع.

## إعادة الاستخدام والهجرة

تستعمل كيانات المجال والعقود وقواعد النشر والأجهزة والاستحقاق الموجودة عند صلاحيتها؛ لا يُنقل plugin هاتف أو مصدر Demo إلى لوحة إنتاج. لوحات Flutter في debug تبقى مرجعاً حتى تسليم البديل، ثم إزالتها شريحة مستقلة باختبارات. لا أثر بيانات إنتاجية حالياً؛ عند تغير عقود الخادم أو صدورها يلزم خطة توافق وإصدارات.

## بوابات القبول

API يرفض الطالب لكل مسار إدارة ولو عرف URL؛ جلسة الويب لا تعتمد على قيمة دور محلية. تحدد حماية الجلسة وCSRF وCORS وفق التصميم بعد حسم التقنية. كل عملية كتابة تراجع المدخلات والنطاق والنسخة وتؤكد النتيجة الموثوقة. الإيصال أو OCR لا يمنح وصولاً أو ينشر علامات من نفسه. صور كشف كل الطلاب لا تصل إلى الطالب؛ السجل read-only، ونجاح اختبار Flutter لا يعد اختباراً للوحة الويب.
