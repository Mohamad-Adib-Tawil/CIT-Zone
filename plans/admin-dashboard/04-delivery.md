# 04 — تسليم التصميم وتنفيذه والتحقق منه

## مخرجات التصميم قبل البرمجة

1. **خريطة تنقل نهائية** للهاتف واللوحي، مع أسماء عربية معتمدة لكل وجهة وعلاقة الصفحات ببعضها.
2. **تصاميم منخفضة التفاصيل** للرئيسية، قائمة المحتوى، محرر الدورة، الطلاب، طلب نقل الجهاز، وحالات الفراغ والخطأ. تثبت ترتيب العناصر قبل اختيار الزخرفة.
3. **تصاميم مرئية عالية التفاصيل** بوضع فاتح وداكن، في عروض منطقية مرجعية `320dp` و`360dp` و`600dp` و`1024dp`، مع حالة تكبير خط ونص عربي طويل.
4. **مكتبة مكونات** تضم حالات الأزرار والحقول والبطاقات والشرائح والبحث والمرشحات والحوارات ومؤشرات الرفع. لكل مكون توثيق للحالات العادية والمعطلة والخاطئة.
5. **نموذج تفاعلي** لثلاث رحلات: نشر دورة، منح استحقاق، نقل جهاز؛ يُختبر مع مسؤول إداري فعلي إن أمكن.
6. **خريطة بيانات لكل شاشة** توضح المصدر والحقول اللازمة وتعريف كل مؤشر وحالة عدم التوفر، قبل تثبيت عقد API.

## مراحل التنفيذ

### A — الأساس البصري والتنقل

- اعتماد اتجاه الهوية النهائي والشعار والخط بعد تجربة عربية على الهاتف.
- بناء `ThemeData` فاتح/داكن ورموز تصميم مركزية، و`AdminShell` متكيف، وحارس توجيه دور الإدارة.
- تنفيذ عناصر مشتركة محدودة: `AsyncStateView`، `StatusChip`، `FilterBar`، `ConfirmActionSheet`، وقائمة كيان متكيفة.

**قبول المرحلة:** يمكن الانتقال بين الوجهات على هاتف ولوحي مع RTL وتكبير نص دون قص، وتُرفض صفحة الإدارة قبل التحقق من الدور.

### B — الرئيسية والمحتوى

- بناء واجهة الرئيسية ببيانات تجريبية منفصلة عن الواجهة أثناء التطوير فقط، ثم توصيلها بعقد API الحقيقي قبل الإطلاق.
- تنفيذ المنهج وقوائم المواد والدورات وتفاصيل/محرر الدورة، ثم الدروس والوسائط والمرفقات.
- نقل فحص الجاهزية والنشر إلى الخادم؛ الواجهة تعرض النتيجة ولا تستنتج وحدها أن النشر آمن.

**قبول المرحلة:** تنفذ الإدارة رحلة دورة كاملة، ويظهر الدرس الأول مجانياً في معاينة الطالب، ولا تتكرر الدورة عند ظهور المادة في موضعين.

### C — الطلاب والعمليات الحساسة

- تنفيذ قائمة الطلاب والتفاصيل والاستحقاقات وطلبات نقل الأجهزة وسجل الإجراءات.
- لكل إجراء حساس، اربط التأكيد بنتيجة خادم مسجلة، مع منع الإرسال المكرر وحالات التعارض.

**قبول المرحلة:** تتطابق الحالة التي تعرضها الواجهة مع الخادم بعد إعادة فتح الصفحة، ويرفض الخادم طالباً يحاول استدعاء مسارات الإدارة.

### D — الصقل والتحقق

- جرّب على أجهزة Android/iOS حقيقية وهاتف صغير ولوحي، في RTL، وفي الوضعين الفاتح والداكن، وعند تكبير الخط.
- راجع الأداء والوصول ووضوح الرسائل وسهولة إكمال المهام. أصلح المشكلات قبل إضافة رسوم تجميلية أو مؤشرات جديدة.

**قبول المرحلة:** تنجح مهام النشر والمنح والنقل دون لبس للمسؤول، وتنجح معايير الشاشة والواجهة المدرجة أدناه.

## تنظيم Flutter المقترح عند التنفيذ

```text
lib/
  core/theme/                  # ألوان، كتابة، مسافات، ThemeData
  features/admin/
    presentation/
      shell/                   # التنقل المتكيف وحارس الصفحة
      overview/                # page + cubit + widgets
      curriculum/              # list/detail/editor + cubits
      courses/                 # list/detail/editor + cubits
      media/                   # library/upload status + cubits
      students/                # list/detail + cubits
      entitlements/            # list/grant flow + cubits
      device_requests/         # list/detail/decision + cubits
      audit/                   # read-only list/detail + cubit
      settings/                # preferences/profile
      widgets/                 # المشترك الحقيقي فقط
    domain/                    # كيانات الإدارة وحالات الاستخدام والعقود
    data/                      # DTO وAPI repositories
```

هذا تفصيل داخلي للميزة يتسق مع [المعمارية العامة](../02-architecture.md). لا تُنشأ كل المجلدات مسبقاً؛ أنشئها عند بدء شاشاتها. استخدم Cubit مستقل للقائمة والمحرر عند اختلاف دورة حياتهما؛ لا تضع منطق النشر والتفويض داخل Widget أو Cubit واحد شامل لكل الإدارة.

## بيانات API المطلوبة للشاشات

| الشاشة | الحد الأدنى للعقد قبل توصيلها |
| --- | --- |
| الرئيسية | مؤشرات معرفة بدقة + `asOf` + قائمة مهام عاجلة + نشاط حديث + حالة جزئية لكل مصدر |
| قوائم المحتوى | ترقيم، بحث، ترتيب، مرشحات، إجمالي معروف أو إشارة لعدم توفره |
| محرر الدورة | نسخة/وقت تعديل، أخطاء حقول، نتيجة فحص جاهزية، نتيجة النشر |
| الوسائط | حالة الرفع والمعالجة منفصلتان، تحديث حالة آمن، سبب الفشل المسموح عرضه |
| الطلاب | بيانات عرض دنيا، استحقاقات، حالة الجهاز دون أسرار أو معرفات خام |
| طلبات الأجهزة | حالة الطلب وسبب القرار المسموح وتاريخ التغييرات ومرجع تدقيق |
| السجل | ترقيم، نطاق زمني، نوع الفعل، مسؤول، هدف، نتيجة، معرف طلب |

لا تُثبت أسماء JSON أو مسارات الشبكة قبل حسم منصة الخادم وكتابة عقد API. يجب أن تتطابق حالات المجال مع [خطة الإدارة](../06-admin-api.md).

## معايير قبول التصميم

- تظهر أول مهمة قابلة للتنفيذ من الرئيسية دون أكثر من نقرتين، وتفتح إلى الكيان الصحيح.
- لا يختفي «حفظ المسودة» أو «نشر الدورة» بسبب لوحة مفاتيح الهاتف أو تكبير الخط.
- يميّز المسؤول بصرياً ونصياً بين `draft` و`processing` و`ready` و`published` و`failed`.
- عند فشل بطاقة مؤشر واحدة لا تُفقد بقية بيانات الصفحة، ولا تُعرض قيمة صفر بديلة عن خطأ.
- يمكن إكمال البحث والمرشحات والعودة من التفاصيل مع بقاء موضع القائمة والمرشحات.
- تظهر رسالة أثر قبل النشر أو المنح أو نقل الجهاز، والنتيجة الدائمة بعد نجاح الخادم.
- لا تكشف صفحات الطلاب والسجل بيانات حساسة أو روابط/مفاتيح وسائط.
- لا توجد عناصر تفاعلية غير عاملة في نسخة قابلة للإطلاق.
- اختبارات شاشة عند `320/360/600/1024dp`، وضع أفقي، تكبير نص، RTL، فاتح/داكن، مع TalkBack وVoiceOver عند توفر الأجهزة.
- التباين ومساحات اللمس وتسميات عناصر الواجهة تُفحص وفق [أدوات Flutter للوصول](https://docs.flutter.dev/ui/accessibility/accessibility-testing).

## قرارات تمنع اعتماد الشكل النهائي

- `D11`: لوحة داخل تطبيق الطالب أم تطبيق Flutter إداري منفصل. لا يغيّر ذلك لغة التصميم، لكنه يؤثر في دخول الإدارة والتنقل والتوزيع.
- `D15`: هل دور إدارة واحد يكفي أم يلزم إظهار أفعال مختلفة بحسب صلاحيات أدق؟
- هوية العلامة: الشعار والخط والألوان النهائية. القيم الحالية نماذج تصميم، وليست ملف هوية معتمداً.
- بيانات «الرئيسية»: مؤشرات إضافية أو رسوم زمنية لا تُضاف قبل تعريفها وتوفرها من الخادم.
