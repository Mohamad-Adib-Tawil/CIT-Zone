# 03 — رحلات الإدارة وحالات الواجهة

> مرجع تصميم/تنفيذ Flutter بتاريخ سبتمبر 2026. في 2026-10-08 اعتمدت لوحة **ويب مستقلة**، وأُلغي نطاق الإدارة داخل تطبيق الطالب للإنتاج. اقرأ [نطاق لوحة الويب](README.md) و[التسليم الجديد](04-delivery.md) أولاً؛ أمثلة Widgets/Cubits والاختبارات الأصلية لا تعني اختيار Flutter Web أو اكتمال لوحة الويب. الوظائف والشاشات الإضافية في الفهرس الجديد جزء من النطاق المعتمد.

## رحلة نشر دورة

1. من «المحتوى»، تختار الإدارة مادة موجودة أو تنشئها ثم تفتح مسودة دورة مرتبطة بأستاذ وصفي واحد.
2. تضيف درساً أول بعنوان وملخص وفيديو؛ يظهر بوضوح أنه معاينة مجانية. تضيف بقية الدروس ومرفقاتها.
3. ترفع الفيديو وتتابع حالته حتى `ready`. تعرض الواجهة نجاح رفع الملف منفصلاً عن نجاح معالجته.
4. تضغط «فحص الجاهزية». يجيب الخادم بقائمة أخطاء قابلة للإصلاح: لا درس أول، فيديو غير جاهز، موضع مكرر، معلومات ناقصة، أو حماية وسيط غير مضبوطة.
5. تعرض شاشة المراجعة ما سيظهر للطالب: اسم المادة والأستاذ وترتيب الدروس ومجانية الدرس الأول ومواضع الظهور. بعد تأكيد صريح ترسل عملية نشر واحدة قابلة للإعادة بأمان.
6. تعرض نتيجة الخادم؛ عند النجاح تظهر الحالة `published` ووقت النشر، وعند التعارض تُحدّث المسودة ويظهر سبب واضح. لا يُفترض النشر لمجرد إغلاق الحوار.

## رحلة منح استحقاق

1. من تفاصيل الطالب أو صفحة الاستحقاقات، تختار الإدارة الطالب والدورة والمدة ومصدر المنح والسبب.
2. يعرض ملخص قبل التنفيذ: الطالب، المادة، وقت البداية والنهاية، وهل سيظهر الوصول فوراً.
3. يتحقق الخادم من صلاحية المسؤول وقيود التكرار والتواريخ ويسجل العملية ذرياً.
4. عند النجاح، يظهر الاستحقاق في قائمة الطالب مع مرجع تدقيق. عند التعارض، تعرض الواجهة الاستحقاق القائم وخيارات المعالجة المعتمدة، دون تكرار صامت.

## رحلة نقل جهاز

1. يظهر الطلب في قائمة «يحتاج إلى إجراء» وفي صفحة الطلبات.
2. تفتح الإدارة التفاصيل وتراجع إثبات الطالب وسياسة النقل المعتمدة، ثم تختار قبولاً أو رفضاً مع سبب.
3. قبل القبول، تعرض الواجهة أثر الإبطال وحد الرخص القديمة دون اتصال. ترسل العملية للخادم بمفتاح يمنع التكرار.
4. يظهر القرار والوقت والمسؤول، ويرى الطالب رسالة واضحة في التطبيق. لا تقول الواجهة «تم حذف الفيديو من الجهاز السابق» لأن ذلك لا يمكن ضمانه وهو غير متصل.

## حالات مشتركة لكل شاشة

| الحالة | المعالجة البصرية | السلوك |
| --- | --- | --- |
| تحميل أولي | هيكل مطابق لشكل المحتوى، دون قفزات كبيرة | ألغِ الطلب إن غادرت الصفحة ولم تعد نتيجته لازمة |
| تحديث جزئي | البيانات السابقة مع مؤشر تحديث غير حاجب | لا تُصفّر الأرقام أثناء التحديث |
| فراغ حقيقي | رسالة تشرح السبب + إجراء مناسب، مثل «أضف أول دورة» | لا تعرض فراغاً إذا فشل الطلب |
| خطأ شبكة | رسالة قصيرة وزر إعادة محاولة | احتفظ بالمرشحات والمسودة المحلية المسموح بها |
| صلاحية مرفوضة | حالة وصول صريحة، مع خروج/تحديث جلسة إن لزم | لا تعرض بيانات محمية من ذاكرة صفحة قديمة |
| تعارض تعديل | نسخة أحدث/تغيير متزامن مع مراجعة الفرق | لا تستبدل تعديل مسؤول آخر بصمت |
| إجراء جارٍ | زر مع مؤشر تقدم وتعطيل التكرار | لا تسمح بنقرات متتابعة تنشئ طلبات مكررة |
| نجاح | حالة محدثة في موضع العنصر + رسالة قصيرة | لا تعتمد على SnackBar وحده |

## قواعد كتابة الرسائل

- استعمل فعلاً محدداً: «تعذر نشر الدورة: فيديو الدرس الأول ما زال قيد المعالجة»، بدلاً من «حدث خطأ» فقط.
- رسائل الرفض الإداري تشرح ما يمكن فعله تالياً، دون عرض معلومات داخلية أو رموز أمنية.
- الأزرار الحساسة تحمل الفعل وموضوعه: «نشر الدورة»، «نقل الجهاز»، «منح الوصول»، لا «تأكيد» فقط.
- التاريخ والحالة متاحان بالنص لقارئ الشاشة؛ لا تعتمد على شارة ملونة وحدها.

## حالات حافة يجب تصميمها قبل التنفيذ

- لا توجد مواد أو طلاب بعد؛ كل شاشة تشرح خطوة البدء.
- مادة تظهر في أكثر من موضع، مع دورة واحدة واشتراكات واحدة.
- فيديو رُفع ثم فشلت معالجته؛ إعادة المحاولة لا تخلق درساً مكرراً.
- المسؤول يبدأ تعديل دورة ثم تنتهي جلسته أو يغادر بغير حفظ.
- مسؤولان يعدلان الدورة نفسها؛ يظهر تعارض نسخة بدلاً من فقد تعديل أحدهما.
- طالب يملك استحقاقاً قائماً، ثم يحاول مسؤول منحه استحقاقاً متداخلاً.
- طلبا نقل جهاز متزامنان للطالب نفسه.
- API المؤشرات يعمل بينما API النشاط يفشل؛ تبقى الرئيسية مفيدة مع بيان الجزء الفاشل.
- تكبير الخط أو تضييق النافذة يحول الجدول إلى عرض مناسب دون قص الأفعال.
